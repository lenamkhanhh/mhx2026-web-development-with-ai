# Collaboration data extension

This approved migration keeps collaboration inside the four existing
workbench screens. It does not introduce a new product area or Firebase
Storage.

## Firestore paths

```text
trips/{tripId}/notes/{noteId}
trips/{tripId}/subitems/{subitemId}
trips/{tripId}/activity/{activityId}
```

Each note and sub-item has an `eventId`, so the Timeline detail panel can
render it without a nested subscription per event.

## Documents

### Notes

```text
eventId: string
body: plain string, 1..1000 characters
createdBy: uid
createdAt: server timestamp
```

Members may create notes. The author or trip lead may delete a note. Notes are
plain text and render through React text nodes only.

### Sub-items

```text
eventId: string
title: plain string, 1..160 characters
completed: boolean
createdBy: uid
createdAt: server timestamp
updatedAt: server timestamp
```

Members may create sub-items. The author or trip lead may update or delete a
sub-item. This deliberately keeps completion attribution out of the initial
schema; the record is a planning checklist, not an attendance or payment log.

### Activity

```text
kind: "note_added" | "subitem_added" | "subitem_completed" | "subitem_reopened"
eventId: string
actorId: uid
label: plain string, 1..220 characters
createdAt: server timestamp
```

Activity is append-only, actor-attributed, and generated by the repository in
the same batch as the corresponding note/sub-item mutation. It is useful UI
context, not a trusted forensic audit trail: a server-side audit service would
be needed for that stronger guarantee.

## Explicit exclusions

- Files are not stored because Firebase Storage plus Storage Rules is not in
  the approved deployment configuration.
- Join-by-code remains fail-closed until a callable/server-verifiable flow is
  introduced.
